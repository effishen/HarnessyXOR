Projects, teams and permanent history

HarnessyXOR 0.2.0-alpha.1 is a fresh project-first foundation. A workspace owns settings and projects. Each project starts with a principal architect; teammates belong to that same project.

Start a project

  1. Configure your existing OpenAI-compatible or Ollama model in Settings.
  2. Create a workspace and a project. For existing source, upload and extract it during the initial baseline phase, then finalize the unverified baseline before sending your first Architect message. Empty projects can start directly.
  3. Talk to the architect. Inspect Team to follow assigned agents and tasks; their conversations are read-only details.
  4. Use Knowledge for current requirements and accepted, proposed, rejected or superseded decisions.
  5. Activate a regression catalog in Regression, then inspect proposals, reviews, checks and acceptance in Changes.

Source and working copies

Canonical source is in Files/Project-<project-id>_output/. Private Git metadata, agent copies and candidate checkouts are under .harnessyxor/projects/<project-id>/. Generic file tools cannot read or write Git metadata. Development and testing agents change their own copies; the architect reads accepted source and reviewers inspect assigned candidates.

Baseline finalization or your first Architect message closes ordinary canonical file editing. Later code changes use proposals. Existing dirty source is preserved and blocks integration instead of being reset.

What acceptance means

A proposal binds its base, integrated commit/tree, catalog and project-context revisions. Distinct independent code and architecture approvals and one complete controller-run active suite are required. New user guidance or changes to source, requirements, decisions, policy or catalog stale older evidence.

Comments do not clear a blocking review. Retired tests and agents retain their history. A model claiming PASS is not an observed test result.

Current execution limits

The native runner supports file existence, required text, JSON validity and Git whitespace checks. Command checks need isolated candidate execution. Manual and hardware checks need operator evidence. These unavailable checks stay pending and block acceptance; compilation and simulation never substitute for a physical test.

Raw model shell execution is unavailable in this foundation. There is no host fallback. Automatic VM provisioning, physical-evidence capture, remote Git hosting and native host verification require further work.

Accounts and diagnostics

Create your first account on the host with harnessyxor account create <username>. Session expiry is disabled; sign-out and password reset revoke sessions. Diagnostics exclude project files, conversations, credentials and raw model/tool payloads.

Validation limits

Private automated checks exercise the actual Rust application and synthetic model services. Native macOS/Windows, real model inference, actual guest/hardware paths and browser rendering have separate verification requirements.
